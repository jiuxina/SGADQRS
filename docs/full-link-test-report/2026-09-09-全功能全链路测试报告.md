## 4. 缺陷清单

### BUG-1 (P1) 批量禁用/启用用户功能完全不可用
- **现象**：勾选用户 → 批量禁用 → 确认 → toast 报「状态不能为空」，后端状态不变（已 API 复核 status 仍为 1）。
- **根因**：前端 `frontend/src/api/modules/user.ts:43` 只发 `{ ids }`；后端 `BatchUserDTO` 要求 `status` 为 `@NotNull`（UserController.java:107 → BatchUserDTO.java:15）。
- **修复建议**：前端按语义发 `{ ids, status: 0|1 }`（并补批量启用入口），或后端给 status 默认值。

### BUG-2 (P1) 批量删除用户功能完全不可用
- **现象**：批量删除 → 确认 → 400「请求体格式错误或必填参数缺失」，用户未被删除。
- **根因**：前端发 `{"ids":[61,60]}`（user.ts:40）；后端 `@RequestBody List<Long> ids` 要求是**裸 JSON 数组**（UserController.java:94）。前端多包了一层 `ids` 键。
- **修复建议**：前端改发 `[...ids]`。注：API 层边界套件用裸数组测试是通过的——**前后端契约不匹配只有端到端测试能暴露**。

### BUG-3 (P1) 教师提交的竞赛（status=1）无 UI 途径流转为已发布，形成报名死角
- **现象**：教师「提交审核」创建的竞赛 status=1；学生列表/详情**可见**但详情页无报名入口；系统 Lean 后无竞赛审核角色。学生建队要求 status∈{2,3}，若无人干预该竞赛永远无法被报名。
- **佐证**：后端允许教师 `PUT /competition` 携带 `status=2` 完成流转（本次测试即以此解锁故事线），但前端创建/编辑表单不提供该操作（提交恒为 1，编辑保存不改状态）。
- **修复建议**：① 教师端为 status=1 竞赛提供「发布」动作（PUT status=2）；或 ② 创建表单去掉「提交审核」语义、创建即 status=2；或 ③ 学生列表不再展示 status=1 竞赛。
- **回归提示**：`e2e/teamup.spec.ts` 与手工路径均依赖已发布竞赛，此缺陷影响新竞赛全流程。

### BUG-4 (P2) 顶栏页面标题滞后一拍
- **现象**：位于 `/admin/users` 时 document.title 正确显示「用户管理 · 赛友 TeamUp」，但顶栏可见标题显示上一页的「竞赛中心」；同样 /admin/competitions 显示「系统总览」。每次导航都滞后一次。
- **定位**：`DesktopLayout` 顶栏 titleMap 取值时机晚于/早于路由更新（疑与 PageTransition 配合有关）。

### BUG-5 (P2) 弹窗/确认框关闭后长时间残留（opacity:0 未卸载）
- **现象**：「新增用户」弹窗关闭后仍挂载于 DOM，与后续打开的「编辑用户」弹窗**双表单并存数分钟**（两套 h3 与全套输入框同时存在，截图前状态）。本次测试实际发生**向隐藏表单误填、保存丢失用户改名**的事故。
- **影响**：真实用户风险较低（视觉不可见），但污染可访问性树（屏幕阅读器可读出双弹窗）、干扰自动化与浏览器插件；残留的确认框透明蒙层理论上可吞点击。
- **备注**：本测试环境 rAF 节流使 motion 退出动画不结束，放大了残留时长；**建议在正常 Chrome 复核残留时间**，并考虑 AnimatePresence 的 `onExitComplete` 强制卸载。

## 7. 测试环境备注（非系统缺陷）
1. **IAB 截图偶发白屏假象**：DOM 完整且样式可见时截图为空白，强制重绘后恢复（见 `evidence/03b-users-page-repaint.png` 对比）。已确认非应用问题。
2. **动画页面的 Playwright actionability 超时**：登录页/弹窗存在持续动画，标准 click/check 挂起，需 JS 派发点击。对真实用户无影响。
3. **确认框堆叠**：本环境中弹窗退出动画不结束 → 关闭的确认框以 opacity:0 残留，自动化点击可能命中旧弹窗（部分操作需重试）。放大了 BUG-5 的暴露，也解释了部分用例的重试现象。
4. **文件上传未覆盖**：IAB 不支持 file chooser，头像/竞赛封面/附件上传仅验证了表单入口与大小/类型校验文案存在，实际上传链路由 `boundary_full.py`（白名单/413/路径穿越 7 项断言）覆盖。
5. 历史遗留：本次发现并恢复了种子 `community_request` id=2（此前测试周期丢失）。

## 8. 结论与建议

**结论**：系统整体质量良好——API 层 303 项断言全绿、UI 端到端主流程（登录→建赛→组队→社区互看/申请→审核→成绩→通知→导出）全链路闭环、越权与过期会话防护有效、全程零前端崩溃。**但「用户批量操作」两个 P1 契约缺陷使管理员该功能 100% 不可用，且「教师提交的竞赛无法在 UI 内发布」的 P1 状态机死角会阻断新竞赛的全部报名流程**，建议优先修复后再做演示/答辩。

**优先修复顺序**：
1. BUG-1 / BUG-2（各一行代码级修复：补 `status` 字段、改裸数组）
2. BUG-3（建议创建即发布，或在教师列表加「发布」操作）
3. BUG-4（顶栏标题联动）、BUG-5（弹窗卸载时机，需正常浏览器复核）
4. P3 三项体验一致性

**测试证据**：`docs/full-link-test-report/evidence/`（01 管理员仪表盘、02 删除确认弹窗、03b 用户管理页重绘后截图）

**建议纳入回归**：修复后重跑 `smoke_full.py` + `boundary_full.py`，并按本报告 §3 用例表抽查批量操作与竞赛发布路径。
