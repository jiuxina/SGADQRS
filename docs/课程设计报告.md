## 一、需求分析

### （一）系统概述

本系统名为"赛友 TeamUp"（原 SCMS，Student Competition Information Management System），是一个面向高校的学生竞赛信息管理平台。系统采用前后端分离架构，支持管理员、教师、学生三种角色，覆盖竞赛发布、组队招募、参赛审核、成绩录入、消息公告等全流程业务。

### （二）用户需求分析

1. **管理员**：拥有系统最高权限，负责管理所有用户（增删改查、启用/禁用、批量操作、重置密码）、管理全部竞赛、审核参赛队伍（提交→通过/拒绝）、录入和发布成绩、管理系统公告（富文本编辑、置顶、草稿）、查看全局统计数据（用户分布、竞赛热度、报名趋势、奖项分布）并导出 Excel/CSV。

2. **教师**：是竞赛的创建者，负责发布竞赛（创建即发布、发布即报名，无审核环节，自定义奖项、上传附件、设置时间节点）、编辑自己发布的竞赛、查看自己竞赛的队伍与参赛者名单（只读指导，不参与审批）、录入和发布成绩（支持 CSV 批量导入）。

3. **学生**：是竞赛的参与者与社区主体，负责浏览已发布的竞赛、创建队伍报名（单人赛视为 1 人队，创建即提交）、队伍内成员流动（退队、队长移除成员、转让队长；队长指定指导老师，老师只读）、通过招募广场与入队申请/邀请加入队伍、查看已发布的成绩与成绩单、浏览他人社区主页、接收站内通知、管理个人资料（修改信息、更换头像、修改密码）。

### （三）功能需求分析

系统需实现以下核心功能：

1. 用户认证与授权：支持三种角色登录，基于 JWT 的无状态认证，角色级权限控制。
2. 竞赛全生命周期管理：竞赛创建即发布（发布即报名）、编辑、进行中、已结束的状态流转（时间到期自动转换）。
3. 团队组建与审核：学生创建/加入团队、成员流动（退队/移除/转让队长）、队长指定指导老师（只读）、管理员审核队伍。
4. 成绩管理：教师录入/发布成绩、支持 CSV 批量导入、学生查看已发布成绩。
5. 社区功能：组队招募/求组帖发布（可留联系方式）、入队申请/邀请（可附备注）、社区资料卡与公开主页。
6. 站内通知系统：互动通知、全员公告、未读计数（含浏览器标签页角标）。
7. 数据统计与导出：管理员仪表盘、报名趋势、竞赛排行、Excel/CSV 导出。

### （四）非功能需求分析

1. **安全性**：密码采用 BCrypt 哈希存储，JWT 令牌 24 小时有效期，接口级权限校验。
2. **可用性**：响应式设计，支持桌面端和移动端访问；iOS 26 Liquid Glass 玻璃态设计语言。
3. **可维护性**：前后端分离、RESTful API 设计、MyBatis-Plus ORM 简化数据库操作。
4. **性能**：Docker 容器化部署 MySQL、分页查询、索引优化。

## 二、概念结构设计

### （一）E-R 图设计

本系统采用实体-关系（E-R）模型进行概念结构设计。系统共包含 8 个核心实体，实体之间通过外键关联建立联系。E-R 图如下所示：

```
┌──────────────┐ 发布 1:N    ┌──────────────────┐ 组建 1:N    ┌──────────────────┐
│   sys_user   │───────────→│   competition    │───────────→│ competition_team │
│   (用户表)    │              │   (竞赛信息表)    │              │   (参赛队伍表)    │
└──┬─────┬──┬──┘              └──┬──────────┬────┘              └────┬──────┬──────┘
   │     │  │参与/成绩/发帖/       │产生 1:N  │冗余竞赛ID             │包含  │队长/指导
   │     │  │请求/接收 1:N        ▼          ▼ (一人一赛一队)          1:N  │1:N
   │     │  │            ┌──────────────┐ ┌────────────────────┐          │
   │     │  └────────────│ competition_ │ │ competition_team_  │◀─────────┘
   │     │               │ result       │◀│ member             │
   │     │               │ (竞赛成绩表)  │ │ (团队成员表)        │
   ▼     ▼               └──────────────┘ └────────────────────┘
┌──────────────┐  产生 1:N   ┌──────────────────┐      ┌──────────────────┐
│ recruit_post │───────────→│community_request │      │sys_notification  │
│ (招募/求组帖) │              │ (社区请求表)      │      │ (站内通知表)      │
└──────────────┘              └──────────────────┘      └──────────────────┘
```

> 完整字段级关系详见 `docs/ER-DIAGRAM.md`（Mermaid 版 E-R 图，与 `backend/sql/init.sql` 同步维护）。

### （二）实体说明

| 实体名 | 中文名 | 说明 |
|--------|--------|------|
| sys_user | 用户表 | 存储学生、教师、管理员三种角色的用户信息，含社区昵称、技能标签等社交属性；角色由 user_type 唯一推导 |
| competition | 竞赛信息表 | 竞赛的基本信息、时间安排（报名窗口即组队准入窗口）、奖项设置（JSON）、附件列表（JSON） |
| competition_team | 参赛队伍表 | 竞赛中的团队（报名与队伍合一，单人赛=1人队），含队长、指导老师、审核状态 |
| competition_team_member | 团队成员表 | 团队与学生的多对多关联；冗余竞赛ID + 双唯一键在库层强制"一人一赛一队" |
| competition_result | 竞赛成绩表 | 学生的竞赛成绩记录（一人一行），支持按竞赛发布 |
| recruit_post | 组队招募/求组帖 | 学生发布的组队招募或求组信息，可选留联系方式（微信/QQ/邮箱） |
| community_request | 社区请求表 | 入队申请、入队邀请两种类型的社交请求（早期"资料互看"类型已下线，存量仅作历史） |
| sys_notification | 站内通知表 | 互动通知和全员公告（user_id=0 表示全员公告） |

### （三）实体关系说明

1. **用户与竞赛**：一个用户（教师/管理员）可以发布多个竞赛（1:N）。
2. **竞赛与队伍**：一个竞赛可以有多个参赛队伍（1:N），单人赛视为 1 人队；报名与队伍合一，不设独立报名表。
3. **队伍与成员**：一个队伍包含多个成员（1:N），通过 team_id 和 student_id 关联；成员表冗余 competition_id，配合唯一约束在数据库层强制"一名学生在同一竞赛只能属于一支队伍"（1:N 的竞赛-成员关系 + 唯一性约束）。
4. **竞赛与成绩**：一个竞赛产生多条成绩记录（1:N），成绩按人存储，队伍上下文由 team_id 承载。
5. **用户与招募帖**：一个用户可以发布多个招募/求组帖（1:N）；招募帖必须关联发布者本人担任队长的队伍。
6. **招募帖与社区请求**：一个帖子可以产生多条入队申请/邀请（1:N），请求同时关联双方用户与队伍。
7. **用户与通知**：一个用户可以接收多条通知（1:N），user_id=0 为全员公告。

## 三、逻辑结构设计

### （一）关系模式设计

本系统共设计 8 张数据表，所有表间关系为逻辑外键，由应用层保证一致性。命名采用下划线命名法，字段名同样使用下划线命名法。所有表使用 InnoDB 存储引擎，字符集为 utf8mb4。

#### 1. sys_user（用户表）

| 字段名 | 数据类型 | 约束 | 说明 |
|--------|---------|------|------|
| id | BIGINT | PRIMARY KEY, AUTO_INCREMENT | 主键 |
| username | VARCHAR(50) | NOT NULL, UNIQUE | 登录账号 |
| password | VARCHAR(100) | NOT NULL | 密码（BCrypt 哈希） |
| real_name | VARCHAR(50) | NOT NULL | 真实姓名 |
| nickname | VARCHAR(50) | DEFAULT NULL | 社区昵称（展示名优先昵称，无昵称回退真实姓名） |
| avatar | VARCHAR(255) | DEFAULT NULL | 头像 URL |
| gender | TINYINT | DEFAULT 0 | 性别：0-未知 1-男 2-女 |
| user_type | TINYINT | NOT NULL | 用户类型：1-学生 2-教师 3-管理员 |
| dept_name | VARCHAR(50) | DEFAULT NULL | 所属学院 |
| major_name | VARCHAR(50) | DEFAULT NULL | 专业 |
| class_name | VARCHAR(50) | DEFAULT NULL | 班级 |
| bio | VARCHAR(500) | DEFAULT NULL | 个人简介 |
| skills | VARCHAR(255) | DEFAULT NULL | 技能标签（逗号分隔） |
| status | TINYINT | NOT NULL, DEFAULT 1 | 状态：1-启用 0-禁用 |
| create_time | DATETIME | NOT NULL, DEFAULT CURRENT_TIMESTAMP | 创建时间 |

## 四、物理结构设计

### （一）数据库环境

| 配置项 | 值 |
|--------|-----|
| 数据库管理系统 | MySQL 8.0 |
| 部署方式 | Docker 容器（容器名：mysql-scms） |
| 端口映射 | 3306:3306 |
| 字符集 | utf8mb4（支持 emoji 等 Unicode 字符） |
| 排序规则 | utf8mb4_general_ci |
| 存储引擎 | InnoDB（支持事务、行级锁、外键） |
| 连接地址 | jdbc:mysql://localhost:3306/scms |

### （二）索引设计策略

1. **主键索引**：所有表均使用 BIGINT 自增主键，InnoDB 聚簇索引按主键物理排序存储。
2. **唯一索引**：sys_user.username 保证登录账号唯一；competition_team_member 的 uk_tm_team_student（team_id+student_id）防重复入队，uk_tm_comp_student（competition_id+student_id）把"一人一赛一队"业务规则下沉到数据库层，作为并发场景下应用层校验之外的最终兜底。
3. **查询索引**：
   - competition 表：status 和 publisher_id 建立普通索引，优化按状态和发布人筛选。
   - competition_team 表：competition_id 和 teacher_id 建立普通索引，优化按竞赛和指导老师查询。
   - competition_team_member 表：team_id 普通索引 + 两个唯一键（兼具查询功能）。
   - competition_result 表：competition_id、student_id、is_published 分别建立索引，优化多维度查询。
   - community_request 表：to_user_id+status 组合索引、from_user_id 索引、from_user_id+to_user_id+type 组合索引，优化社交请求查询。
   - sys_notification 表：user_id+is_read 组合索引优化未读通知查询，ref_type+ref_id 组合索引支持通知跳转回查。

### （三）存储过程与触发器

本系统不使用存储过程和触发器，所有业务逻辑由应用层（Spring Boot 后端）实现。状态转换（如竞赛状态自动更新）在 Service 层的查询方法中自动完成。

### （四）数据备份策略

生产环境建议采用以下备份策略：
1. 使用 `mysqldump` 定期全量备份数据库。
2. 开启 MySQL 二进制日志实现增量备份。
3. 备份文件存储在独立的备份服务器或云存储中。

### （二）核心功能模块原型设计

#### 1. 核心功能模块 1：登录页面

**1.1 页面布局**

登录页面采用分屏布局设计。左侧面板：全屏竞赛主题图片，叠加暗色渐变遮罩，鼠标移动时产生视差效果。右侧面板：玻璃态（Glassmorphism）表单卡片，包含角色切换器（管理员/教师/学生三选一）、用户名输入框、密码输入框（支持显示/隐藏切换）、"记住账号"复选框、登录按钮（loading 状态）。登录失败时表单触发抖动动画。

**1.2 页面功能及数据设计**

用户选择角色后输入用户名和密码，前端调用 `POST /api/auth/login` 接口提交 `{username, password, role}`，后端通过 BCrypt 验证密码，检查角色是否匹配，成功后返回 JWT 令牌和用户信息。前端将令牌存入 localStorage（key: `scms_token`），用户信息存入 localStorage（key: `scms_user`），并根据角色跳转到对应仪表盘。涉及表：`sys_user`。

#### 2. 核心功能模块 2：管理员-用户管理页面

**2.1 页面布局**

页面顶部为指标卡片区域，显示用户总数、学生数、教师数、管理员数（带 DigitRoller 数字滚动动画）。下方为操作栏：角色筛选 chips、防抖搜索框、批量操作按钮（全选、批量删除、批量禁用）。主体为分页数据表格，每行显示用户名、姓名、角色、院系、状态、创建时间。操作列包含编辑、切换状态、重置密码、删除按钮。页面弹窗用于创建/编辑用户（含头像上传）。

**2.2 页面功能及数据设计**

管理员可对用户进行增删改查操作。查询功能支持按角色筛选和关键字模糊搜索，调用 `GET /api/user/list` 接口；创建用户调用 `POST /api/user` 接口（默认密码 123456）；更新用户调用 `PUT /api/user` 接口；删除用户调用 `DELETE /api/user/{id}` 接口；批量操作调用 `POST /api/user/batch-delete` 和 `POST /api/user/batch-disable` 接口；重置密码调用 `PUT /api/user/reset-password/{id}` 接口。涉及表：`sys_user`。

#### 3. 核心功能模块 3：管理员-数据统计页面

**3.1 页面布局**

页面顶部为日期范围筛选器（默认近 6 个月）。下方为 8 个指标卡片（用户总数、竞赛总数、团队总数、成绩总数等），带 AnimatedCounter 数字动画。主体区域分为两列：左侧为报名趋势柱状图（纯 SVG 实现，无图表库），右侧为竞赛热度 Top 10 排行榜（进度条可视化）。底部为奖项分布柱状图和 CSV 导出按钮。

**3.2 页面功能及数据设计**

管理员查看系统全局统计数据。调用 `GET /api/stats/admin` 接口获取综合统计（用户分布、竞赛状态分布、团队数量、报名趋势、竞赛排行、奖项分布）；调用 `GET /api/stats/enrollment-trends` 获取近 6 个月报名趋势数据；调用 `GET /api/stats/competition-rankings` 获取竞赛热度 Top 10。CSV 导出在客户端生成，使用 BOM 处理中文编码。涉及表：`sys_user`、`competition`、`competition_team`、`competition_result`。

#### 4. 核心功能模块 4：教师-创建竞赛页面

**4.1 页面布局**

页面为长表单布局。顶部为竞赛名称输入框。表单区域包含：封面图上传区（支持图片预览）、主办单位、竞赛描述、竞赛规则。奖项管理区域支持动态添加/删除奖项（名称+等级）。时间安排区域包含 4 个日期选择器（报名开始/截止、竞赛开始/截止），有时间顺序校验。底部为地点、最大队员数设置（1 表示个人赛）。提交按钮为"发布竞赛/保存并发布"——创建即发布（status=2），无审核环节；编辑模式按原状态保存（进行中/已结束不回退）并额外显示附件管理区域。创建模式表单草稿自动暂存 localStorage，刷新可恢复。

**4.2 页面功能及数据设计**

教师创建竞赛时，填写完整表单后调用 `POST /api/competition` 接口提交（包含 `CompetitionDTO` 对象）。编辑已有竞赛调用 `PUT /api/competition` 接口。封面图通过 `POST /api/file/upload` 上传后返回 URL。奖项以 JSON 数组格式存储。时间校验确保：报名开始 < 报名截止 < 竞赛开始 < 竞赛结束。涉及表：`competition`。

#### 5. 核心功能模块 5：教师-成绩管理页面

**5.1 页面布局**

页面顶部为竞赛选择下拉框。选择竞赛后显示统计卡片（均分/最高分/最低分，带 AnimatedCounter 动画）。下方为成绩分布直方图（SVG 实现）。主体为分页成绩数据表格，每行显示学生姓名、团队名称、分数、排名、奖项等级、评语、发布状态。操作列包含编辑成绩按钮。页面提供批量录入弹窗（支持 CSV 导入）和"发布所有成绩"按钮。

**5.2 页面功能及数据设计**

教师选择竞赛后，调用 `GET /api/result/list` 接口获取该竞赛的成绩列表（仅自己发布的竞赛）。编辑单条成绩调用 `PUT /api/result` 接口（通过 `EditGradeDialog` 弹窗）。批量录入支持 CSV 文件导入，调用 `POST /api/result/batch` 接口。发布成绩调用 `POST /api/result/publish/{competitionId}` 接口，将 `is_published` 设为 1。统计信息调用 `GET /api/result/stats` 接口获取。涉及表：`competition_result`、`competition_team`、`sys_user`。

#### 6. 核心功能模块 6：学生-竞赛浏览与报名页面

**6.1 页面布局**

竞赛浏览页面顶部为防抖搜索框和状态筛选 chips。主体为 4 列卡片网格，每张卡片包含：竞赛封面图、竞赛名称、状态徽章、主办单位、描述截断文本、元数据（报名时间/地点/人数/竞赛时间）、CountdownTimer（报名倒计时，<24h 时进入紧急模式）、操作按钮（"查看详情"，进入详情页后再走报名/参赛入口）。报名成功触发 ConfettiEffect 粒子庆祝动画（150 个粒子，持续 3 秒）。

竞赛详情页面为完整信息展示：封面图 + 标题头、2x2 信息网格（时间/地点/人数/状态）、竞赛简介（HTML 渲染）、竞赛规则、奖项设置（按等级排序，金银铜色背景）、竞赛附件（可下载列表）。底部操作按钮：返回列表 / 立即报名。

**6.2 页面功能及数据设计**

学生浏览竞赛列表调用 `GET /api/competition/list` 接口，系统自动附加参赛队伍数和当前用户是否已参赛。报名与队伍合一：通过 `EntryModal` 弹窗创建队伍调用 `POST /api/registration/team` 接口（表单含团队名称、口号、指导老师选择），服务端校验竞赛状态与报名窗口（registration_start/end 之外拒绝）；单人赛（max_members=1）自动组成 1 人队并直接提交审核；团队赛创建后进入"组建中"状态，由队长提交审核。同一学生同一竞赛只能属于一支队伍（应用层查重 + 数据库唯一键双重保证）。涉及表：`competition`、`competition_team`、`competition_team_member`。

#### 7. 核心功能模块 7：学生-团队组建页面

**7.1 页面布局**

页面为"组队中心"，含四个内层 Tab："我的队伍"（卡片网格：团队名称、状态徽章、竞赛名称、口号、队长标识、指导老师、成员列表；提供创建队伍与提交审核/解散入口）、"招募广场"（招募/求组帖卡片列表：标题、类型标签、竞赛名称、方向标签、截止时间、发布者资料卡与联系方式；支持发帖弹窗）、"收到的申请/邀请"（待处理优先）、"发出的请求"。队伍详情页（TeamDetail 子页）中成员行提供退队、移除成员、转让队长的内联操作（仅组建中/被驳回状态可用）。

**7.2 页面功能及数据设计**

学生创建队伍调用 `POST /api/registration/team` 接口（自动成为队长）。招募帖/求组帖调用 `POST /api/recruit` 接口创建（招募帖必须关联本人任队长的队伍，可选联系方式 contact）；浏览调用 `GET /api/recruit/list` 接口，支持按竞赛、类型、关键字筛选。入队路径统一走社区请求：向招募帖队长发起入队申请（type=2）或由队长向求组帖作者发起入队邀请（type=3），调用 `POST /api/community/request` 接口；接收人经 `PUT /api/community/request/{id}/handle` 同意后自动入队，服务端依次经过快失败预校验（报名窗口/满员/一人一赛一队）→ 队伍行锁 + 成员数 FOR UPDATE 当前读 → 成员表双唯一键兜底，满员自动关闭招募帖。成员流动调用 `PUT /api/registration/team/{id}/leave`（退队）、`DELETE /api/registration/team/{id}/member/{studentId}`（移除）、`PUT /api/registration/team/{id}/leader/{studentId}`（转让队长）。涉及表：`competition_team`、`competition_team_member`、`recruit_post`、`community_request`。

#### 8. 核心功能模块 8：学生-参赛历史与成绩页面

**8.1 页面布局**

页面顶部为 3 个指标卡片（参赛总数/通过审核/获奖次数），带 DigitRoller 动画。下方为时间线视图，将报名和成绩数据合并为时间线条目，按最近活动时间排序。每条时间线包含：竞赛名称、生命周期阶段（报名/审核通过/被拒/参赛中/已评分/获奖）、4 点进度条可视化（报名→审核→参赛→评分）、可展开详情面板。成绩单导出按钮位于页面右上角。

**8.2 页面功能及数据设计**

学生查看参赛历史调用 `GET /api/registration/teams` 接口（学生身份自动过滤为我所在队伍，可与 `GET /api/result/list` 的已发布成绩合并渲染时间线）。查看成绩调用 `GET /api/result/list` 接口（系统强制筛选 `is_published=1`，防止越权拉取未发布数据）。个人成绩统计调用 `GET /api/result/student/stats` 接口。导出成绩单调用 `GET /api/export/student-transcript` 接口，生成 Excel 文件供下载。涉及表：`competition_team`、`competition_team_member`、`competition_result`、`competition`。

#### 9. 核心功能模块 9：管理员-参赛队伍审核页面

**9.1 页面布局**

队伍审核位于"竞赛管理"页面的"队伍"内层 tab，为分页数据表格布局：顶部为竞赛筛选、状态筛选和队名搜索框。表格每行显示队伍名称、所属竞赛、队长、成员数、提交时间、状态徽章。操作列：待审核（已提交）状态显示"通过"和"驳回"按钮（驳回经 RejectReasonModal 输入意见）；任意状态可进入队伍详情子页（成员、指导老师、竞赛上下文）。

**9.2 页面功能及数据设计**

队伍审核链：队长建队（0 组建中）→ 提交审核（1 已提交，名单冻结、关联招募帖自动下架）→ 管理员审核（`PUT /api/registration/team/{id}/audit?status=2|3`，仅"待审核"可审，防重复审核；结果通知全队成员；被驳回的队可修改名单后重新提交）。并发控制：审核与退队/移除/转让/入队共用队伍行 `SELECT ... FOR UPDATE` 锁，保证状态机串行流转。删除竞赛（`DELETE /api/competition/{id}`）级联删除相关队伍、成员、招募帖、成绩。涉及表：`competition`、`competition_team`、`competition_team_member`、`recruit_post`、`competition_result`。

#### 10. 核心功能模块 10：通知中心页面

**10.1 页面布局**

页面顶部为"标记全部已读"按钮。主体为通知列表，每条通知包含：类型图标（公告/互动/系统）、标题、内容摘要、时间、已读/未读状态指示。全员公告（user_id=0）以不同样式高亮显示，支持置顶。未读通知数量显示在导航栏的 `NotificationBell` 组件上（30 秒轮询更新）。

**10.2 页面功能及数据设计**

学生查看通知列表调用 `GET /api/notification/list` 接口，支持按未读状态筛选。获取全员公告调用 `GET /api/notification/announcements` 接口。未读通知计数调用 `GET /api/notification/unread-count` 接口（前端 30 秒轮询，驱动铃铛角标、标签页标题与 favicon 角标）。标记单条已读调用 `PUT /api/notification/read/{id}` 接口。标记全部已读调用 `PUT /api/notification/read-all` 接口。点击通知按 `ref_type`（request/recruit/team/user/notice）+ 标题关键字跳转到对应落地页（组队中心相应内层 tab、招募广场、我的队伍、成绩单）。涉及表：`sys_notification`。

## 七、总结与体会

### （一）技术性总结

本项目采用前后端分离架构，前端使用 React 19 + TypeScript + Vite 8 + Tailwind CSS 4 技术栈，后端使用 Spring Boot 3.2.5 + MyBatis-Plus 3.5.6 + MySQL 8 技术栈。在数据库设计方面，通过 E-R 模型完成概念结构设计，将系统从最初 15 表经两轮经确认的精简重构收敛为 8 张核心数据表：报名与队伍合一（删除报名表）、公告并入通知表、隐私字段不入库；采用逻辑外键由应用层保证一致性，但对"一人一赛一队"这类必须绝对成立的规则，通过成员表冗余竞赛 ID + 双唯一索引把约束下沉到数据库层，作为并发场景下应用层校验之外的最终兜底；对队伍状态变更与容量校验统一使用 `SELECT ... FOR UPDATE` 当前读加行锁，解决了 REPEATABLE READ 隔离级别下快照读漏看并发插入导致的超员问题；使用 JSON 字段存储奖项和附件等非结构化数据，有效减少了表的数量和关联复杂度；种子演示数据的报名窗口采用相对时间（`NOW() ± INTERVAL`），避免库表随时间老化失效。在安全认证方面，实现了基于 JWT 的无状态认证机制，密码采用 BCrypt 哈希存储且序列化不外发，通过 Spring Security 实现角色级权限控制并在服务层收紧数据范围（教师限本人发布的竞赛、学生仅见已发布成绩）。在前端状态管理方面，使用 Zustand 轻量级状态库管理认证与通知未读状态，通过 localStorage 实现状态持久化。在 UI 设计方面，采用 iOS 26 Liquid Glass 玻璃态设计语言，通过 Tailwind CSS 和 Motion 动画库实现了现代化的用户界面。系统配套 Python 无依赖回归脚本（冒烟/边界容错/成员流动专项）与幂等演示数据生成器，保证每次改动可全量回归验证。

### （二）非技术性总结

通过本次课程设计，小组成员深入理解了数据库系统原理的核心知识，包括需求分析、概念结构设计（E-R 模型）、逻辑结构设计（关系模式）、物理结构设计（索引策略、存储引擎选择）的完整流程。在团队协作方面，5 名成员分工明确，分别负责架构设计、后端开发、前端开发和测试文档工作，通过 Git 进行版本控制和协作。在项目管理方面，采用了模块化开发策略，前后端并行开发，通过 RESTful API 进行对接。在问题解决过程中，我们遇到了 Docker 容器配置、CORS 跨域、JWT 令牌管理、中文文件名编码等多个技术挑战，通过查阅文档和团队讨论逐一解决，提升了实际工程能力。
